# Browser command and draft recovery

The browser retains the exact encrypted pending campaign command before sending it. Reload recovers that command identity and payload, subscribes to its bound authoritative receipt and retries the same admission. It never creates a replacement order merely because acknowledgement was interrupted. Receipt acceptance/rejection clears only the matching pending record.

The recovery slot belongs to an account, independently of preview URL. An atomic IndexedDB write prevents two tabs replacing one another's pending command. Storage failure blocks submission with an explicit remedy; there is no unrecorded-send fallback. Account changes clear in-memory data and require the new account's authorization before recovering its own records. Local records are not an authorization source. A corrupted record stops recovery before transmission. Forgetting it requires an explicit confirmation that a server-accepted order remains effective; the deletion compares the exact reviewed record so another tab’s replacement cannot be removed.

Conversation drafts use the campaign's explicit encryption provider, with account/campaign/room and revision bound to the envelope. Real drafts use the protected real ingress key with a separate derived storage key; mock drafts remain inspectable development data and never use or disclose a real key. Keys are fetched through the existing session-fenced endpoints and are not persisted beside the encrypted records. Draft keys use HKDF separation from ingress keys and are cached only in memory until authentication changes. Browser storage is not end-to-end secrecy or protection against an active authenticated script compromise.

Unsent drafts restore into the authorized conversation only. Losing membership hides protected draft content until access is established. Concurrent draft edits preserve the local text and require an explicit choice before replacing another tab's saved draft. The editor distinguishes recovering, saving, saved and conflict states. Closing a browser before its saved acknowledgement can lose the latest unsaved keystrokes; no unload-time write is claimed. Send waits for draft persistence and stores its exact encrypted command before network admission. Acceptance clears only the matching saved text; newer edits remain intact. Authoritative accepted messages remain the history source; local drafts and pending envelopes are not presented as sent messages.

This continues milestones 8/10 and the shared command-recovery contract. It adds no gameplay rule or new server service. Implementation is complete for this slice; exact-head CI, hosted Google acceptance and independent security/rendered review remain gates. No backend or ingress deployment is required: the browser uses the existing fenced key endpoints, command admission and bound receipts.

## Evidence

The expanded ordinary-player mock journey passes in 44.7 seconds. The final managed-key journey passes in 1.4 minutes, alongside seven production gallery/lab cases (eight tests total, 1.8 minutes). The journey covers unsent-draft reload, two-tab draft conflict, a competing order rejected before any transport write, pending-order reload/retry, exactly one command identity/payload and one sequence increment, accepted-draft clearing, removal/rejoin, corrupted-record confirmation, storage failure with zero admitted writes, and switching away from and back to the original account. Encrypted records carry the correct provider/algorithm and no separate persisted key.

The scenario uses ordinary identity, campaign, conversation and recovery controls. A service-clock campaign start and injected browser storage/transport failures are explicit test controls; no game state or backend service is mocked. Before-scroll primary-action containment, bounded scrolling, target geometry, keyboard focus and reduced-motion outcomes are checked. [Captured states](../ux/reviews/command-recovery/) include phone draft conflict, pending recovery, invalid record and phone/desktop/short/4K conversations.

Types and lint pass; the existing 73-unit suite passes 1,358 assertions. Backend logic is unchanged from #29’s both-provider and complete service verification. Replacement verification for #27–29 remains monitored; a passing local journey does not certify those pending runs.

The first browser pass exposed a self-conflict after accepted-draft cleanup advanced the saved revision; the editor now reloads that revision. Later failed fixtures targeted Firebase’s authentication database instead of the recovery database, requested a creation control while still in a selected campaign, and navigated before sign-out completed. No assertions were removed to conceal a duplicate logical command or lost draft.

## Remaining scope

Conversation history sharing, alliances/exchanges and the broader return briefing remain separate work. Local recovery records are per browser; this is not cross-device draft synchronization. Existing campaign membership and key revocation rules still govern server access. Future ingress-key rotation must include an explicit local-record compatibility policy; no silent key fallback is implemented.
